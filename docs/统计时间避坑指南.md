# AgentForge 统计时间避坑指南

> 这是 [项目避坑指南](项目避坑指南.md) 的姊妹篇。上一篇讲"项目怎么跑起来、数据怎么对上"，
> 这一篇只讲**时间统计**：Trace 里的耗时、Token 里的用量、以及"账平了但时间是假的"这件事。
>
> 来源：2026-11-09 的 M1 收尾会话。所有数字都来自真实请求的 `/api/traces/{id}` 返回。
>
> 状态标记：✅ 已修 / ⚠️ 仍未修（现在还是这样）/ 📌 口径约定

---

## 0. 一句话结论

**"数字对得上"不等于"时间是真实的"。**

现在的执行树是：

```
1 个真实总时长 + N 个真实工具耗时 + 1 个倒推值 + 1 条拼出来的时间轴
```

子节点加起来正好等于根，是因为**倒推**（总时长 − 工具耗时）在凑账，
不是因为每个节点都被认真测过。先把这句话记住，后面所有坑都是它的展开。

---

## 1. 先统一口径：这些"时间"不是一回事

| 指标 | 谁量的 | 真实吗 | 覆盖范围 |
|---|---|---|---|
| `latencyMs`（根 `agent.run`） | Java `ChatService`，`System.currentTimeMillis()` 包住 `agentRuntimeClient.run()` | ✅ 真实 | 网络 + FastAPI + 所有 LLM + 所有工具 + Python 序列化；**不含** Java 写库、组装返回 |
| 工具 `duration_ms` | Python `run_tool` 前后的 `perf_counter()` | ✅ 真实 | 单个工具的"开始到返回" |
| `route`（`code_agent`） | 无，写死 `0` | ❌ 假 | 路由是 `return "code_agent"` 的纯函数，本来也不花时间，但 0 是写死的，不是量的 |
| `answer` | Java `latencyMs - toolMillis` 倒推 | ❌ 假 | 所有 LLM 调用之和，不是"最后生成答案"那一下 |
| `started_at` / `ended_at` | Java 按步骤顺序用 `cursor` 累加 | ❌ 拼的 | 不是真实发生时刻，只是"长度对得上的时间轴" |
| `tokens`（Trace 页） | `message.total_tokens`，按 `span.message_id` 查 | ✅ 真实 | 一条助手消息的 token 总量（多次 LLM 累加） |

**结论**：时间类能直接相信的只有两个数——根的总时长、工具耗时。
其余都是派生值或展示值，排查性能问题时不要把 `answer` 当成"模型生成答案花了多久"。

**顺带一个口径不一致**：`trace_span.span_type` 的建表注释写的是
`llm / tool / retrieval / internal`，代码 `mapSpanType` 实际返回 `agent / tool`，
前端 `SpanType` 又只有 `llm / tool / agent`。三处对不上，加 `llm` 类型时一并统一。

## 2. 一次 9 秒请求的时间账

真实的一条 trace（`ChatService 的 chat 方法做了什么？`）：

```
agent.run        9117ms   ← 根，真实测量
├─ code_agent       0ms   ← 写死
├─ search_code    146ms   ← 真实
├─ search_code     46ms   ← 真实
├─ read_file        0ms   ← 真实，但 <1ms 被截成 0
├─ read_file        0ms
├─ read_file        0ms
└─ answer         8925ms  ← 9117 − 192，倒推
```

`0 + 146 + 46 + 0 + 0 + 0 + 8925 = 9117`，账是平的。

### 2.1 `answer` 为什么是 8925

Python 里 `answer` 的 `duration_ms` 是**整轮**（从第一次调模型前记的 `started_at` 到现在），
这次也是 9117 左右。Java 如果原样落库：

```
9117(根) vs 9117(answer) + 146 + 46 = 9309  → 子节点比根还大
```

所以上一轮修 0ms 时加了倒推：

```java
int toolMillis = steps.stream()
        .filter(s -> "tool_call".equals(s.getType()))
        .mapToInt(s -> s.getDurationMs() == null ? 0 : s.getDurationMs())
        .sum();

if ("answer".equals(step.getType())) {
    durationMs = Math.max(0, latencyMs - toolMillis);
}
```

`8925 = 9117 − (146+46+0+0+0)`。**这个数是 Java 现算的，模型从来没给过任何耗时。**

### 2.2 倒推的代价：把 4 次思考压成一个节点

这次请求里模型被调用了 4 次（每轮工具之后各一次），真实时间分布大概是：

```
想 2s → 搜 146ms → 想 1.8s → 搜 46ms → 想 2.2s → 读 3 次（略）→ 想 2.7s → 回答
```

但树上是：

```
工具 192ms + answer 8.9s（所有思考的合计）
```

你能得到的信息只有"模型总共花了 8.9 秒"，得不到"第几轮慢、为什么慢"。
**账平了，信息没了。**

## 3. 统计时间的九个坑

### 3.1 `duration_ms` 被 Jackson 静默丢掉，全变 0 ✅

**现象**：Python 已经返回 `duration_ms: 146`，Java 落库全是 0。

**原因**：`AgentStep.java` 只声明了 `type/tool/args/status/result_count` 五个字段，
Jackson 默认忽略未知字段，`duration_ms` 不报错、不进对象，
`AgentTraceService` 只能写 `0`。

**做法**：

```java
@JsonProperty("duration_ms")
private Integer durationMs;
```

**怎么验**：`/api/traces/{id}` 里 `search_code` 的 `durationMs` 不再是 0。

**顺带一个坑**：如果你在 IDE 里找不到 `AgentStep.java`，先确认打开的是
`/Library/Java/AgentForge-迁移包-20261108/AgentFile`，不是 10-09 的旧副本
`/Library/Python_Project/agentforge`——旧副本的 `dto/` 里没有这个文件，
这跟 Flyway 校验失败是同一个根因（见主指南 §1.7）。

### 3.2 Python 的 `answer.duration_ms` 是整轮，不是"生成答案" ⚠️

**现象**：直接落库会导致子节点总和大于根。

**原因**：`react_loop.py` 在循环结束后补了一条 `answer` 步骤，
它的 `duration_ms = time.perf_counter() - started_at`，而 `started_at` 在第一次调模型**之前**，
所以它是"整轮"，已经包含所有工具和所有 LLM。

**做法**：要么让 Python 把它改成"最后一次 LLM 调用耗时"（推荐，见 §6），
要么在 Java 里扣掉工具耗时（现状）。**不能原样用**。

### 3.3 倒推能凑账，但会编造时间分布 ⚠️

**现象**：`answer` 8.9 秒，看起来像"生成答案特别慢"。

**原因**：四轮 LLM 的时间被合并成一个数字，放在最后一个节点上。

**代价**：

- 无法定位"哪一轮慢"（提示词太长？上下文变大？工具返回太多？）；
- 加新步骤（RAG 的检索、重排）后，减法逻辑要重写；
- 答辩时被问"为什么回答要 9 秒"，只能答"模型慢"，说不出细节。

**判断标准**：如果一条 trace 里"子节点之和 == 根"精确成立，八成有倒推；
真实测量应当允许**子节点之和 ≤ 根**，差额是网络/序列化/未插桩的开销。

### 3.4 毫秒取整把 `read_file` 变成 0ms ⚠️

**现象**：`read_file` 三个节点全是 0ms，看起来像没计时。

**原因**：Python `int((perf_counter() - tool_started) * 1000)`，本地读文件 <1ms，
整数截断就是 0。**这是真实值，不是 bug。**

**做法**（按需要选）：

- 保持 0，并在文档/UI 里说明"0ms 表示 <1ms"；
- 或 `Math.max(1, durationMs)` 让"发生过"的步骤至少显示 1ms；
- 或把口径改成微秒（`duration_us`），展示时再换算。

### 3.5 `route` 的 0ms 是写死的 ⚠️

`react_loop.py` 里 route 步骤直接写 `"duration_ms": 0`。
路由确实是纯函数，但"0"不是量出来的。以后路由变成 LLM 分类器时，
这里必须改成真实计时，否则树会继续骗人。

### 3.6 `started_at` / `ended_at` 是拼出来的时间轴 ⚠️

**现象**：树看起来有先后顺序，但时间戳不是真实时刻。

**原因**：`AgentTraceService.completeTask` 里：

```java
LocalDateTime cursor = rootStartedAt;
for (AgentStep step : steps) {
    LocalDateTime startedAt = cursor;
    LocalDateTime endedAt = cursor.plusNanos(durationMs * 1_000_000L);
    cursor = endedAt;
}
```

它只知道每段多长，不知道真实开始时刻，于是从 `task.startedAt` 开始一段段往后排。
真实情况是"模型思考/工具调用交替"，代码把它拉成了一条直线。

**还有一个边界**：`rootStartedAt` 取的是 `task.startedAt`（建任务时），
而 `latencyMs` 是从"开始调 Python"起算的，两者差几毫秒，
所以根的 `ended_at` 会比真实结束稍晚。**看趋势可以，别拿它做精确对齐。**

### 3.7 总耗时取根，不要再 sum ⚠️（已在主指南 §2.4 修）

`getTrace` 如果对根 + 子一起 `sum`，总耗时会翻倍。
正确写法：

```java
response.setDurationMs(roots.isEmpty() ? 0 : roots.get(0).getDurationMs());
```

### 3.8 0ms 的兄弟节点时间戳相同，排序不稳定 ⚠️

**原因**：`cursor` 在 `durationMs == 0` 时不变，三个 `read_file` 的 `started_at` 完全一样；
`started_at` 是 `DATETIME(3)`，只到毫秒，0ms 节点必然并列；
`TraceSpanRepository` 只按 `started_at ASC` 排序，没有第二排序键。

**后果**：同一时刻的兄弟节点，数据库返回顺序不保证，前端树的顺序可能抖动。

**做法**：仓库方法加 `id` 兜底排序（`OrderByStartedAtAscIdAsc`），
或者按 `task_step.step_index` 排；差异只在展示层，不影响总账。

### 3.9 时钟源和单位要统一 📌

- Java 用 `System.currentTimeMillis()`：**墙钟**，系统校时/NTP 跳变会让差值为负；
  量耗时更稳的是 `System.nanoTime()`。
- Python 用 `time.perf_counter()`：**单调**，适合量耗时，但不能和墙钟互转。
- 两边都存"毫秒整数"，跨进程比较时只比**持续时间**，不要比绝对时刻。
- 展示层直接输出 `{{ span.durationMs }}ms`：`384000ms` 这种数字对用户不友好，
  后续加个 `formatDuration`（<1s 显示 ms，≥1s 显示 s）。

## 4. Token 统计：另一个"永远是 0"

### 4.1 `trace_span` 表里没有 token 列 ✅

有人会以为 span 上存了 token，其实没有。`trace_span` 的列是：

```
id, trace_id, conversation_id, message_id, parent_span_id, task_id,
step_id, tool_call_id, name, span_type, status, input, output,
attributes, started_at, ended_at, duration_ms, error_message, created_at
```

token 存在 `message` 表：

```
prompt_tokens, completion_tokens, total_tokens
```

全项目写这三个字段的只有 `ChatService`（保存助手消息时），
`AgentTraceService` 一次都没写过 token。

### 4.2 为什么 Trace 页显示 0 ✅

`getTrace` 只读了 `trace_span` 一张表，然后：

```java
response.setTokens(0);   // 占位，从来没算过
```

不是"数据丢了"，是"没人把两张表接起来"。

### 4.3 正确接法：顺着 `message_id` 查一次 ✅

```java
int tokens = 0;
for (TraceSpan span : spans) {
    if (span.getMessageId() != null) {
        tokens = messageRepository.findById(span.getMessageId())
                .map(m -> m.getTotalTokens() == null ? 0 : m.getTotalTokens())
                .orElse(0);
        break;
    }
}
response.setTokens(tokens);
```

- 取第一个带 `messageId` 的 span 就够：一次 trace 的所有 span 都指向同一条助手消息；
- **不要遍历 span 求和**：消息里的总数已经是"这一轮所有 LLM 调用之和"，求和会翻倍；
- 旧 trace 也能补上：旧 span 也写了 `message_id`，改完查历史记录一样有值，不用重跑对话。

### 4.4 聊天页的 token 和 Trace 页的 token 是两个来源 📌

| 位置 | 来源 | 什么时候会是 0 |
|---|---|---|
| 聊天气泡下的 `15936 tokens` | `message.total_tokens` | 消息没落库 / 模型没返回 usage |
| Trace 详情的「Token 消耗」 | `/api/traces/{id}` 的 `tokens` | span 没有 `message_id`（失败任务）/ 消息被删 |

排查时先看是哪一页，不要拿聊天页的数去证明 Trace 页坏了。

### 4.5 token 不是"按 span 摊派"的 ⚠️

模型接口按"一次调用"返回 `usage`，Python 把多轮累加成一个总数。
如果要做"每个 span 花多少 token"，得改三处（加列、Python 按 step 记录、Java 落库），
但收益不大——思考分散在多轮，摊到步骤上并不准确。M1 保持"一条消息一个总数"即可。

## 5. 统计和超时是一回事

这条很容易被忽略：**你统计出来的耗时，决定了超时该配多少。**

- 2026-11-09 实测一条请求跑了 **384012ms**（模型单轮 40~80 秒 × 4~5 轮）；
- 当时 `AgentRuntimeClient` 的读超时是 **180 秒**，所以走 `/api/chat` 必失败；
- 已改成 **600 秒**（`agent.runtime.timeout-seconds`，可用 `AGENT_RUNTIME_TIMEOUT_SECONDS` 覆盖）；
- 但 `SseEmitter` 还是 **120 秒**，长请求会先断 SSE。

对齐建议：

| 层 | 现在 | 建议 |
|---|---|---|
| Java → Python | 600s | 保持，或按实测 P99 再调 |
| SSE（`SseEmitter`） | 120s | ≥ 600s，或等待期间发 `: keep-alive` 心跳 |
| 演示 | 一条 6 分钟 | `agent_max_steps` 12 → 6，prompt 里禁止重复搜 |

**一句话**：时间统计不是"事后报表"，它直接决定超时、重试、演示可行性。

## 6. 正确做法：逐次测量（建议，尚未实施）

目标：让树上每个非零节点都有真实的起止，`answer` 只表示最后一次调用。

### 6.1 Python：给每次 `llm_client.chat` 计时

```python
answer_ms = 0

for _ in range(max(1, settings.agent_max_steps)):
    llm_started = time.perf_counter()
    response = llm_client.chat(messages, tools=TOOL_SCHEMAS)
    answer_ms = int((time.perf_counter() - llm_started) * 1000)
    _add_usage(usage, response.get("usage"))

    message = (response.get("choices") or [{}])[0].get("message") or {}
    tool_calls = message.get("tool_calls") or []

    if not tool_calls:
        content = (message.get("content") or "").strip()
        break

    # 这一轮"模型思考"单独记一个 step
    steps.append({
        "type": "llm",
        "tool": "llm",
        "args": {},
        "status": "success",
        "result_count": len(tool_calls),
        "duration_ms": answer_ms,
    })

    # ... 原有的 assistant/tool 回填 ...

steps.append({
    "type": "answer",
    # ...
    "duration_ms": answer_ms,   # 只记最后一次调用，不再用整轮
})
```

### 6.2 Java：删掉倒推

- 删 `toolMillis` 那段；
- 删 `if ("answer".equals(...)) durationMs = latencyMs - toolMillis;`；
- 只保留 `int durationMs = step.getDurationMs() == null ? 0 : step.getDurationMs();`
- `mapSpanType` 加分支：`if ("llm".equals(stepType)) return "llm";`

`llm` 不是新造的类型：`trace_span.span_type` 的建表注释里本来就写着
`llm / tool / retrieval / internal`，只是代码一直没产出过 `llm`。

### 6.3 前端：给 `llm` 一个标签

`web/src/composables/useChat.ts` 的 `describeTool` 加：

```ts
llm: '模型思考',
```

`SpanType` 已经包含 `'llm'`，`TraceTree` 也预留了图标，不需要改组件。

### 6.4 改完的树长这样

```
agent.run        9117ms
├─ code_agent       0ms
├─ llm           2100ms     ← 第一轮思考
├─ search_code    146ms
├─ llm           1800ms     ← 第二轮
├─ search_code     46ms
├─ llm           2200ms
├─ read_file        0ms
├─ read_file        0ms
├─ read_file        0ms
└─ answer        2700ms     ← 最后一次调用
```

子节点之和会**略小于**根（差几十毫秒的 HTTP/JSON/落库开销）——这是真实的，**不要硬凑**。
一旦你发现自己在"补差额"，说明又回到了倒推的老路。

## 7. 统计口径核对手册

### 7.1 四个检查

1. **每个非零节点都有测量点吗？** 对照 §1 的表，`route`/`answer` 是重点怀疑对象。
2. **子节点之和 ≤ 根吗？** 相等要警惕倒推；略小是正常的。
3. **0ms 是哪种 0？** 没测（route）/ 字段被丢（Jackson）/ 截断（read_file）。
4. **时间戳是真实时刻吗？** 如果所有节点像"排队"一样首尾相接，就是 `cursor` 拼的。

### 7.2 SQL 核对

```sql
-- 一条 trace 的 span 和耗时
SELECT name, span_type, duration_ms, started_at, ended_at, parent_span_id
FROM trace_span
WHERE trace_id = 'trace-xxx'
ORDER BY started_at, id;

-- 根和子是否对得上
SELECT
  MAX(CASE WHEN parent_span_id IS NULL THEN duration_ms END) AS root_ms,
  SUM(CASE WHEN parent_span_id IS NOT NULL THEN duration_ms ELSE 0 END) AS children_ms
FROM trace_span
WHERE trace_id = 'trace-xxx';

-- token 的来源
SELECT id, total_tokens FROM message WHERE id = <span.message_id>;
```

### 7.3 一条 curl 看全貌

```bash
curl -s http://localhost:8080/api/traces/<traceId> | python3 -c "
import json,sys
d=json.load(sys.stdin)['data']
print('spanCount:', d['spanCount'], 'duration:', d['durationMs'], 'tokens:', d['tokens'])
def walk(n, depth=0):
    print('  '*depth + f\"{n['name']} ({n['type']}) {n['durationMs']}ms\")
    for c in n.get('children') or []: walk(c, depth+1)
for r in d['spans']: walk(r)
"
```

预期：`spanCount` 8、只有 1 个根、`tokens` 不是 0（除非消息被删）。
