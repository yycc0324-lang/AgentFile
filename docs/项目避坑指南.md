## 1. 环境与启动

### 1.1 本机端口几乎全被别的项目占着 📌

**现象**：`docker compose up` 起不来，或起来了但连的不是自己的库。

**原因**：这台机器上 3306 被 Homebrew 的 `mysqld` 占着，6379 被 `mineru-redis` 占着，
9000/9001 被 `mineru-minio` 占着。`docker-compose.yml` 里的默认端口全都撞车。

**做法**：只在 `.env` 里覆盖，**不要改 compose，也不要改 application.yml 的默认值**：

```dotenv
MYSQL_PORT=3307
REDIS_PORT=6380
MINIO_API_PORT=9002
MINIO_CONSOLE_PORT=9003
```

compose 直接读 `.env`；`platform-api/src/main/resources/application.yml` 通过
`spring.config.import: optional:file:../.env[.properties]` 读同一份，所以 Java 会跟着用 3307。

**怎么验**：`make config` 通过，`make urls` 打印 3307/6380/9002/9003；
`curl localhost:8080/actuator/health` 返回 UP 说明 Java 连的是 3307。

### 1.2 两个服务必须从各自的模块目录启动 📌

**现象**：在仓库根目录跑 `uv run uvicorn ...`，第一条消息就报「LLM 未配置」；
在根目录跑 jar，Flyway / 数据源连到 3306 而不是 3307。

**原因**：两边的 `.env` 都是**按当前工作目录**找的：

- Python `agent-runtime/app/core/config.py`：`env_file=("../.env", ".env")`
- Java `application.yml`：`optional:file:../.env[.properties]`

从 `agent-runtime/` 启动 → 读到 `AgentFile/.env`；从 `AgentFile/` 启动 → 读不到，
Python 用空 key，Java 退回 `MYSQL_PORT:3306` 默认值。

**做法**：

```bash
cd AgentFile/agent-runtime && uv run uvicorn app.main:app --reload --port 8000
cd AgentFile/platform-api  && java -jar target/platform-api-0.1.0-SNAPSHOT.jar
```

**怎么验**：`curl 127.0.0.1:8000/health` 返回 ok；发一条 `/agent/run` 看 `usage.prompt_tokens > 0`
（等于 0 多半是 key 没读到）。

### 1.3 `make` 只在仓库根目录有效 📌

**现象**：`make: *** No rule to make target 'up'. Stop.`

**原因**：`Makefile` 依赖根目录的 `docker-compose.yml` 与 `.env`，子目录里没有这些。
更隐蔽的是：如果当前目录是 `/Library/Python_Project/agentforge`（10-09 的旧副本），
那里也有一套相似结构，命令能跑但跑的是旧代码。

**做法**：所有 `make` 命令先 `cd /Library/Java/AgentForge-迁移包-20261108/AgentFile`。
IDE、`mvn`、`uv` 同理。旧副本建议删掉或改名，避免再被 IntelliJ/终端认错。

**怎么验**：`git log -1` 是 `e3a5446` 或更新；`pwd` 是迁移包路径。

### 1.4 Qdrant 镜像拉取会卡在 fs layer ⚠️

**现象**：`docker compose up -d` 卡在 `⠹ 4f4fb700ef54 Pulling fs layer` 十几分钟；
`docker images` 里一直没有 qdrant。

**原因**：镜像源网络抖动，跟项目代码无关。M1 的聊天链路不需要 Qdrant，别被它卡住。

**做法**：先做别的；需要时单独拉、换镜像源、或等网络恢复后重试：

```bash
docker pull qdrant/qdrant:latest          # 可加 --platform linux/arm64
docker pull docker.1ms.run/qdrant/qdrant:latest
```

**怎么验**：`docker ps` 里 `agentforge-qdrant` 是 healthy；
`curl 127.0.0.1:6333/healthz` 返回 200。

### 1.5 导入 SQL 必须带 `utf8mb4` 和库名 ⚠️

**现象**：导入报 `ERROR 1046 (3D000): No database selected`；或者导进去了但中文全是乱码。

**原因**：`db/agentforge.sql` 里没有 `USE agentforge;`；连接字符集也不是 utf8mb4。

**做法**：

```bash
docker exec -i agentforge-mysql sh -c \
  'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" --default-character-set=utf8mb4 agentforge' \
  < ../db/agentforge.sql
```

**怎么验**：`SELECT LEFT(content,30) FROM message LIMIT 3;` 中文正常；
`SELECT COUNT(*) FROM flyway_schema_history;` 是 2，且 version 1/2 的 checksum 与迁移包一致。

### 1.6 `project.repo_url` 是绝对路径，换机器必须改 📌

**现象**：Agent 回答永远「没有找到相关代码」，但服务、数据库、key 都正常。

**原因**：`search_code` 按 `repo_url` 找目录，路径不存在时**直接返回空列表**，不报错。
迁移包里存的是旧机路径 `/Library/Py_RT/AgentFile`。

**做法**：

```sql
UPDATE project
SET repo_url = '/Library/Java/AgentForge-迁移包-20261108/AgentFile'
WHERE id = 1;
```

**怎么验**：直接打 Python `/agent/run`，`citations` 不为空；或问「ProjectService 在哪」
能命中 `.java` 文件。

### 1.7 IntelliJ 认错旧工程 → Flyway checksum 校验失败 ✅/⚠️

**现象**：IDEA 启动报 `Flyway Validate failed: Migration checksum mismatch for version 1`，
但命令行 `java -jar` 能正常起。

**原因**：Run Configuration 的 classpath 指向 `/Library/Python_Project/agentforge`
（10-09 的旧副本，HEAD `0634a8c`），两份工程的 `V1/V2` 迁移脚本内容不同：

```
库里记录：2075150577 / -1504376490   ← 迁移包版本
旧副本算：-399156905 / 1757160567    ← 对不上
```

**做法**：

1. IDEA 用 File → Open 打开迁移包目录，不要继续用旧窗口；
2. SDK 选 21，Maven Reload，删掉旧 Run Configuration 重建；
3. Working directory 设成 `platform-api`（这样 `../.env` 才读得到）；
4. 删掉或改名旧副本目录。

**绝对不要**：`flyway repair`。它会把库里的 checksum 改成旧副本脚本的，改完迁移包再也起不来。

**怎么验**：启动日志出现 `Successfully validated 2 migrations` 和 `Schema is up to date`。

### 1.8 上一轮会话的后台进程会占着 8080 / 8000 / 5173 ⚠️

**现象**：自己启动时 `Port 8080 was already in use`，但不知道是谁占的。

**原因**：上一轮为了验证起的 `java -jar` / `uvicorn` / `vite` 还在后台跑；
或者残留的 `docker compose up` 进程。

**做法**：起服务前统一清一遍，并确认是新起的进程：

```bash
lsof -nP -iTCP:8080 -iTCP:8000 -iTCP:5173 -sTCP:LISTEN
lsof -ti:8080 | xargs kill   # 按需
```

**怎么验**：`curl -s -o /dev/null -w '%{http_code}' localhost:8080/actuator/health` 在服务没起时
应该是 000（连接失败），不是 200。

### 1.9 uvicorn 不带 `--reload`，改了代码不生效 ⚠️

**现象**：改了 `react_loop.py`、重启逻辑也对，但行为没变；或者"明明改对了却报旧错"。

**原因**：启动命令没带 `--reload`，进程跑的是旧字节码；更常见的是
**同时存在两个 uvicorn**（一个带 reload 一个不带），请求落到了旧的那个。

**做法**：开发统一带 `--reload`；改完看日志有没有 `Reloading...`；
不确定就 `lsof -ti:8000 | xargs kill` 清干净再起。

### 1.10 数据库快照和 `.env` 都不在 git 里 ⚠️

**现象**：换机器 `git clone` 后，Flyway 建出来的是空表，没有任何项目/会话数据；
或者 `make up` 后连不上库。

**原因**：`db/agentforge.sql` 在仓库外的 `../db/`，`.env` 被 `.gitignore` 忽略且含真实 key。

**做法**：建议把 dump 复制进仓库（`db/agentforge.sql`）再提交——目前还没做，所以 clone 出来只有空表；
`.env.example` 里写清端口覆盖的注释；`.env` 本身永远不提交。新机器按 README + 本文 §1.1/§1.5 恢复。

## 2. Java 平台层

### 2.1 `@Transactional` 不要包住 LLM 调用 ✅

**现象**：并发几条聊天后接口变慢甚至卡死，Hikari 连接池被占满，`task` 一直 running。

**原因**：`ChatService.chat()` 如果加 `@Transactional`，事务会横跨「写消息 → 调 Python（几秒到几分钟）
→ 写结果」整段。事务期间一直占着数据库连接，连接池默认 10 个，几个请求就耗尽。
这次的问题就是「Java 注解把模型思考纳入了事务」。

**做法**：事务只包 DB 写入；外部 HTTP 调用放在事务外。
现在 `ChatService.chat()` 上的 `@Transactional` 是**注释掉**的，并在注释里写明了原因——别"顺手"加回去。
如果以后要保证多表原子性，把 DB 段拆成独立的 `@Transactional` 方法，别把 `agentRuntimeClient.run()` 包进去。

**怎么验**：连续发 5~10 条 `/api/chat`（可以用 `xargs -P`），接口都能返回；
`SHOW STATUS LIKE 'Threads_connected'` 不会持续上涨。

### 2.2 Jackson 会静默丢掉没声明的字段 ✅

**现象**：Python 明明返回了 `duration_ms`，但 Trace 里每个 span 都是 `0ms`。

**原因**：Java 的 `AgentStep` 没有 `durationMs` 字段，Spring Boot 默认
`FAIL_ON_UNKNOWN_PROPERTIES=false`，未知字段**不报错、不警告，直接丢**。

**做法**：Python 返回的每个 snake_case 字段，Java DTO 都要有对应的 `@JsonProperty`：

```java
@JsonProperty("duration_ms")
private Integer durationMs;
```

**怎么验**：`GET /api/traces/{id}` 里 `durationMs` 不为 0；断点看 `AgentStep` 的 `durationMs` 有值。

### 2.3 兜底 `Exception` 会把 404 吞成 50000 ✅

**现象**：前端打开 `/ingest`、`/documents`、`/eval` 页面显示「系统内部错误」，
但后端其实只是**接口没实现**。

**原因**：Spring 6.1 之后找不到映射会抛 `NoResourceFoundException`，
而 `GlobalExceptionHandler` 最后的 `@ExceptionHandler(Exception.class)` 把它也接住了，
返回 HTTP 200 + `code=50000`。

**做法**：加一个更具体的处理器（Spring 优先选最具体的异常类型）：

```java
@ExceptionHandler(NoResourceFoundException.class)
public Result<Void> handleNoResourceFound(NoResourceFoundException e) {
    return Result.error(40400, "接口不存在: /" + e.getResourcePath());
}
```

**怎么验**：`curl -s localhost:8080/api/eval/datasets` 返回 `{"code":40400,...}`。

**注意**：项目的约定是 **HTTP 状态码永远 200，业务结果看 `code`**。
所以排查时不能只看 `curl -f` 是否失败，要看 body 里的 `code`。

### 2.4 Trace 必须有根 span，总耗时不能重复相加 ✅

**现象**：Trace 页 7 个节点平铺成一排，没有父子；总耗时算出来偏大。

**原因**：`completeTask` 只写子 span，成功路径从不写根 span，`parentSpanId` 一直是 null；
`getTrace` 又把 span 平铺返回，前端 `TraceTree.vue` 靠 `children` 递归渲染，自然变成一排。
另外总耗时如果"根 + 子"一起 sum，会算两遍。

**做法**：

1. 写：先存一条 `agent.run` 根 span，循环里 `span.setParentSpanId(root.getId())`；
2. 读：按 `parentSpanId` 在内存里挂树，只返回根节点；
3. 总耗时：`response.setDurationMs(roots.get(0).getDurationMs())`，不要再 sum。

**怎么验**：`/api/traces/{id}` 的 `spanCount` 从 7 变 8，`spans` 只有 1 个根，下面 `children` 有 7 个。
旧数据没有根，仍会平铺，这是正常的。

### 2.5 traceId 必须只有一个来源 ✅

**现象**：Java 日志里的 `trace-xxx` 在 `/api/traces/{id}` 查不到；同一次请求出现两条 trace。

**原因**：Java 生成 `trace-xxx` 传给 Python，但 Python 的 `AgentRunRequest` 没有 `trace_id` 字段，
Pydantic 静默丢弃，Python 又 `uuid4()` 造了一个；成功路径存的是 Python 的，失败路径 `failTask`
用的是 Java 的。

**做法**：Python 侧加字段并原样回显；Java 存 `response.getTraceId()`。

```python
trace_id: str | None = Field(default=None, description="Java 侧生成，原样回显")
```

**怎么验**：响应里的 `traceId` 与 Java 日志里的一致；`/api/traces/{id}` 能查到。

### 2.6 SSE 的三件事 ⚠️

**① POST 不能用 `EventSource`。** `EventSource` 只支持 GET，而 `/api/chat/stream` 是 POST。
必须 `fetch` + `response.body.getReader()` 手动解析（`web/src/composables/useSse.ts` 已经这么做了）。

**② answer 会被推两次。** steps 里有 `type=answer`，controller 又单独发一个 `answer` 事件，
前端渲染成两行（一行"13 条结果"，一行"生成回答"）。循环里要跳过：

```java
if ("route".equals(step.getType()) || "answer".equals(step.getType())) {
    continue;
}
```

**③ 超时对不齐。** `SseEmitter` 是 120s，但 `agent.runtime.timeout-seconds` 是 600s。
模型慢的时候（多轮工具 + 长回答）SSE 会先断。要么把 emitter 超时调到 >= 600s，
要么在等待期间发心跳注释（`: keep-alive`），别让中间层判定连接空闲。

### 2.7 `AgentRuntimeClient` 不设超时，task 会永远 running ✅

**现象**：Python 卡住时，Java 请求既不成功也不失败，`task.status` 一直是 running。

**原因**：`SimpleClientHttpRequestFactory` 默认读超时是"无限等"。

**做法**：显式设置连接/读取超时（5s / 600s，可用环境变量覆盖），并使用
`SimpleClientHttpRequestFactory` 走 HTTP/1.1，避免 JDK HttpClient 的 HTTP/2 升级 + chunked
导致 FastAPI 收到空请求体。

**怎么验**：手动 `kill -STOP` Python 进程，Java 端应在配置的时间内报 50000，并把失败写进 task/trace。

## 3. Python Agent 层

### 3.1 Pydantic 默认忽略未知字段 ✅

**现象**：Java 一直传 `trace_id`，Python 收不到，也不报错。

**原因**：`BaseModel` 默认 `extra="ignore"`，多出来的字段静默丢弃。这比报错更危险，
因为它让"契约不一致"看起来像"功能没生效"。

**做法**：契约字段显式加进模型；开发期可以临时用 `ConfigDict(extra="forbid")` 把不一致暴露出来，
但上线前要评估兼容性。

### 3.2 function calling 的回填协议 📌

**现象**：模型反复调同一个工具；或第二次请求直接 400。

**原因**：工具结果回填格式不对。OpenAI 兼容协议要求：

1. 先把模型这一轮的 `assistant` 消息（含 `tool_calls`）append 进 `messages`；
2. 每个工具结果用 `role="tool"`，并带 `tool_call_id`，**id 必须与调用时一致**；
3. 然后再发下一次请求。

`react_loop.py` 里这两步都要有，少一步模型就"看不见"自己调过什么。

### 3.3 `arguments` 是 JSON 字符串，可能坏 ⚠️

模型给的是 `function.arguments`（字符串），偶尔不是合法 JSON，或者不是对象。
`_parse_arguments` 必须 `try/except` 并回退 `{}`，否则整个请求 500。

同时 `run_tool` 要丢掉模型乱传的 `repo_url` / `blog_path`，统一用服务端注入的值。

### 3.4 引用 ≠ 搜索结果 ✅

**现象**：引用面板 8 条，答案只用了 `ChatService.java`，面板里却混着 `pom.xml`、`http.ts`、
`application.yml`、`useChat.ts`；模型真正读过的 3 段一条都没进面板。

**原因**（三层叠在一起）：

1. `search_code` 返回 5 条命中，代码把 5 条**全当引用**——命中只是候选，不是证据；
2. 搜索在前、读文件在后，引用按"加入顺序"排队，8 条上限**先到先得**，读的永远排最后被砍；
3. 去重键是 `(文件, 行号)`，同一文件读 3 段算 3 条。

这次真实的顺序：两次搜索（5+5 条，去掉 1 条重复 = 9 条）→ 3 次 `read_file`（+3 = 12 条）
→ 最后按加入顺序截到 8 条。读文件永远排在队尾，所以 3 条全被砍；
而答案正文引用的 `ChatService.java:65-76` 恰好来自那 3 次读。

**做法**：拆成两个池子，读过的优先、按文件去重、搜索只兜底：

```python
read_evidence: list[dict] = []   # read_file 读过的
search_hits: list[dict] = []     # search_code 命中的

# 工具成功后按 name 分池；循环结束：
# 读过 → 每文件一条；没读过 → 搜索第 1 名，最多 3 条
citations = _finalize_citations(read_evidence, search_hits)
```

**怎么验**：重发同一条问题，`citations` 条数 = 真正读过的文件数（这次是 1 条），
且 `result_count` 与面板条数一致；`pom.xml`、`useChat.ts` 消失。

**副作用（正常）**：模型只读了 1 个文件时，引用就只有 1 条。面板的价值是"可核对"，不是"数量多"。

### 3.5 `search_code` 是子串匹配，通用词会污染结果 ⚠️

**现象**：搜 `class ChatService`，`pom.xml` 的 `classpath`、`application.yml` 的
`driver-class-name`、`http.ts` 的 `class ApiError` 全都命中；搜 `ChatService chat`，
`llm.py` 的 `def chat(` 拿到 101 分，和真正的 `ChatService.java:42` 并列。

**原因**：

- 抽 token 是 `[A-Za-z0-9_]{2,}`，`class` / `chat` 都会变成独立关键词；
- 匹配是 `token in line`（纯子串），`chat` 命中 `useChat`，`class` 命中 `classpath`；
- 打分规则给 `class|def|function <token>` +100，所以 `def chat(` 也是 101。

**做法**（按性价比排序）：

1. 停用词表：`class/def/function/interface/enum/return/public/private/import/from/package`；
2. 词边界匹配：`(?<![A-Za-z0-9_])chat`，`chat` 命中 `ChatService`、`chat(`，不命中 `useChat`；
3. 工具描述写硬："query 只放具体标识符，不要带 class/def/function"；
4. 长期方案：RAG（embedding 检索），关键词搜索只能做到字面命中。

### 3.6 `read_file` 不返回总行数，模型会重复读 ⚠️

**现象**：同一个文件被读了 3 次，行段还重叠（1-160、88-200、170-240），白烧 token。

**原因**：`read_file` 只返回请求的行段，模型不知道文件一共多少行，只能"试探着读"。

**做法**：返回值加 `total_lines`（和可选的 `truncated`），prompt 里写"文件不超过 300 行时一次读完"。

### 3.7 `list_files` 一次返回太多，prompt 直接上万 token ⚠️

**现象**：一次问答 `prompt_tokens` 14247，其中很大一块是 `list_files` 返回的 69 条目录项。

**做法**：默认 `max_entries` 从 100 降到 40；prompt 约束"除非用户明确问目录结构，否则不要用"。

### 3.8 `showCitations` 必须在生成阶段生效 ✅

**现象**：前端开关关掉，后端仍然返回引用。

**原因**：Java 把 `show_citations` 传下去了，但 `react_loop` 没读；只在返回时清空是不够的，
prompt 里还在要求"必须给引用"。

**做法**：`build_system_prompt(show_citations)` 两套提示词，关闭时去掉引用要求，返回也置空。
这样关掉不只是"不显示"，还省了引用相关的输出 token。

### 3.9 多轮上下文必须由 Java 传过来 ⚠️

**现象**：问完「ChatService 做了什么」，再问「它的第二个方法呢」，模型当成新问题重新搜。

**原因**：Python 按设计不读 MySQL（只有 Java 读写），而 `react_loop` 每次只发
`system + 当前问题`；Java 的 `AgentRunRequest` 也没有 `history` 字段。

**做法**：

- Java 查最近 10 条消息，过滤掉当前这条，塞进 `AgentRunRequest.history`；
- `@Builder.Default` 给空列表，否则 builder 不传时是 null，Pydantic 的 `list` 校验会 422；
- Python 拼成 `[system] + history + [user]`。

**怎么验**：第二问的 steps 里出现 `read_file` 去读同一个文件，而不是重新搜关键词。

### 3.10 `result_count` 要在去重之后算 ✅

**现象**：时间线写"13 条结果"，引用面板只有 8 条。

**原因**：`answer` 步骤的 `result_count` 在去重/截断之前就算好了。

**做法**：先 `_finalize_citations`，再 `len(citations)`。

### 3.11 小坑合集

- `run_react` 里 `steps` 初始化了两次，第一次是死代码，读代码时容易看晕；
- `error` 变量赋值后没用，属于残留；
- `run_react` 是纯函数，**不要**在里面重复 `isinstance` 校验：边界（FastAPI）已经校验过；
  但直接调用时也要构造 `AgentRunRequest`，传 dict 会 `AttributeError`；
- 端点用普通 `def` 而不是 `async def` 是对的：内部是阻塞 `httpx` 调用，写成 async 会卡事件循环。

## 4. 前后端契约与前端

### 4.1 文档写的是 React，代码是 Vue 3 ⚠️

`前端设计与接口文档.md` 里大量 React/组件描述已经过时，`web/` 实际是 **Vue 3 + Vite**。
根目录 `README.md` 也还写着「React 前端 / web 待实现 / 阶段 2」，同样是旧状态。
写答辩材料、改文档前先以 `web/src/` 和 `git log` 为准，别照着旧文档改代码。

### 4.2 前端要的字段名 ≠ 表字段名 ⚠️

- 文档页期望 `{id, name, type, size, status, ingestedAt}`，表里是
  `title / source_type / size_bytes / created_at`；
- 评估页期望 `run.samples[{question, score, status}]`，表里是 `eval_score` 关联。

实现 ingest / eval 之前先把 DTO 定死，再写 Java 转换；不要在 Vue 里做字段映射的"临时补丁"。

### 4.3 业务错误是 HTTP 200 + `code` 📌

前端 `web/src/api/http.ts` 的逻辑：`res.ok` 为真但 `body.code !== 0` 时抛 `ApiError(code, message)`。
所以：

- 新增接口没实现时，先确认返回的是 `40400` 还是 `50000`；
- 页面展示错误时用 `code` 区分"功能没做"和"服务真炸了"；
- `Result.error` 永远 HTTP 200，脚本里别用 `curl -f` 判断成败。

### 4.4 SSE 解析要按"空行分隔"做 📌

`useSse.ts` 的写法是对的：buffer 按 `\r?\n\r?\n` 切块，块内读 `event:` / `data:`，
剩余部分留到下一个 chunk。自己写客户端时注意：

- 一个 chunk 可能只有半行，必须保留 buffer；
- `data:` 里是 JSON，keep-alive 注释行要跳过；
- 事件类型是 `route / step / answer / done / error` 五种。

### 4.5 开发用 Vite proxy，生产要同源 ⚠️

Java 没配 CORS（全仓没有 `@CrossOrigin` / `CorsConfig`）。开发时靠
`web/vite.config.ts` 的 `/api → http://localhost:8080` 代理；生产部署要么 Nginx 同源反代，
要么在 Java 加 CORS，别让浏览器直连 8080。

## 5. 调试与验证

### 5.1 自下而上，不要一上来就说"系统内部错误" 📌

```
Python /health → Python /agent/run（看 traceback）→ Java /api/chat（看契约）
→ /api/chat/stream（看事件顺序）→ 页面（看渲染）
```

Python 的 traceback 只有在直连 8000 时才完整；走 Java 只会被转述成 50000。

### 5.2 三个硬判据

| 判据 | 说明 |
|---|---|
| `usage.prompt_tokens > 0` | LLM 真的被调用了；等于 0 说明还在跑旧逻辑或 key 没读到 |
| `traceId` 与 Java 日志一致 | 双 trace 已修；查不到说明字段又丢了 |
| `citations` 条数 = 读过的文件数 | 引用不再被搜索结果污染；对不上就回看 §3.4 |

### 5.3 出问题先看哪里

- Python 500：看 uvicorn 日志的 traceback（有真实行号）；
- Java 50000 但 Python 正常：先 `curl 8000/health`，再查 `AgentRuntimeClient` 的地址/超时；
- 改了不生效：先确认 `--reload` 生效、有没有第二个进程、跑的是不是旧副本；
- 端口冲突：`lsof -nP -iTCP:<port> -sTCP:LISTEN`。

### 5.4 每次验证都会写库，收尾要清理 ⚠️

每发一条 `/api/chat` 都会写：1 条 message、1 个 task、N 个 step、N 个 tool_call、N+1 个 span。
冒烟测试做多了，库里会堆出一堆假数据（本文写作时已经是 63 消息 / 18 任务 / 101 span）。

**不要背 id**。验证前先把当前最大 id 记下来，按"大于这个值"清理：

```sql
-- 验证前
SELECT MAX(id) AS max_msg FROM message;
SELECT MAX(id) AS max_task FROM task;

-- 验证后（假设验证前 max_msg=63、max_task=18）
DELETE FROM task_step  WHERE task_id  > 18;
DELETE FROM tool_call  WHERE task_id  > 18;
DELETE FROM trace_span WHERE task_id  > 18;
DELETE FROM task       WHERE id       > 18;
DELETE FROM message    WHERE id       > 63;
```

删之前先 `SELECT` 确认范围，别把历史数据一起删了。
迁移包导入后的基线是 **32 消息 / 2 任务 / 6 span**，但后续正常开发会累加，核对时以"验证前快照"为准。
